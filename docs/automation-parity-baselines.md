# Online automation parity baselines

This map identifies existing tests that characterize the currently shipped engine. Most assert old-engine behavior through feature-specific Java or browser paths rather than reusable fixtures for the replacement engine. The `legacyBehaviorBaseline` column in `automation-parity-ledger.csv` stays `not captured` until a versioned scenario records the relevant inputs, state changes, dice, reports and reset outcomes. A captured scenario does not establish full parity for its block.

## Inventory status

`automation-parity-ledger.csv` contains one row for each of the 1,087 automation blocks processed by the current converter dry run. The report classified 1,012 as converter candidates and 75 as unconverted; diagnostics are copied to the corresponding rows. A converter candidate only means the converter accepted the block. It does **not** prove that the replacement has the same behavior.

[`healing-hands.json`](../src/test/resources/dmmt/automation/parity/healing-hands.json) records a seeded successful cast, persisted healer/recipient tracks, report text, invalid self-target, duplicate and locked-target retries, and recipient long-rest expiry. Both the legacy HTTP/WebSocket path and the converted format-2 HTTP path consume the fixture. The converted host protects the stored lock from sheet edits and tests short/long expiry in isolation, not through the unfinished live rest workflow. The fixture does not cover the card's Stress or failure options.

[`healing-hands-outcomes.json`](../src/test/resources/dmmt/automation/parity/healing-hands-outcomes.json) adds
successful clamped Stress recovery, both failure choices and a critical below the written difficulty. Both hosts
exercise choice eligibility, actual recovery, reports, lock creation and duplicate/alternative rejection.

[`warden-protection.json`](../src/test/resources/dmmt/automation/parity/warden-protection.json) records two deterministic report rolls, costs, uses, an unaffordable attempt and rest reset expectations. The legacy browser and converted replacement host consume the same scenario, and the replacement action also has a persisted HTTP/retry test. That coverage does not exercise a live format-2 rest transaction or establish full block parity.

Before cutover, replace remaining `not captured` fields with versioned fixtures containing request/event inputs, deterministic dice, before/after sheet and campaign state, chat/report output and reset/expiry result. Then execute the fixtures against the replacement host and record `parity`, `gap` or `unconverted` per block. Keep known fidelity gaps explicit; do not infer a baseline from labels or converter output.
