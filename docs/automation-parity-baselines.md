# Online automation parity baselines

This map identifies existing tests that characterize the currently shipped engine. Those tests are useful evidence for a future cutover, but they are **not yet reusable golden fixtures** for the replacement engine: most assert old-engine behavior through feature-specific Java or browser paths. The `legacyBehaviorBaseline` column in `automation-parity-ledger.csv` stays `not captured` until inputs, authoritative state changes, dice, reports and persistence outcomes are recorded in a format both implementations can consume.

## Inventory status

`automation-parity-ledger.csv` contains one row for each of the 1,087 automation blocks processed by the current converter dry run. The report classified 1,012 as converter candidates and 75 as unconverted; diagnostics are copied to the corresponding rows. A converter candidate only means the converter accepted the block. It does **not** prove that the replacement has the same behavior.

[`healing-hands.json`](../src/test/resources/dmmt/automation/parity/healing-hands.json) records the first reusable legacy scenario: a seeded successful cast, persisted healer/recipient tracks, report text, invalid self-target, duplicate and locked-target retries, and recipient long-rest expiry. The legacy HTTP/WebSocket test consumes this fixture. It does not establish replacement parity or cover the card's Stress option.

Before cutover, replace remaining `not captured` fields with versioned fixtures containing request/event inputs, deterministic dice, before/after sheet and campaign state, chat/report output and reset/expiry result. Then execute the fixtures against the replacement host and record `parity`, `gap` or `unconverted` per block. Keep known fidelity gaps explicit; do not infer a baseline from labels or converter output.
